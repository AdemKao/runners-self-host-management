# runnerctl v0.5.0 — GitHub-native queued-job scheduler

v0.5.0 changes how runnerctl should enforce host-wide concurrency when GitHub Actions queue semantics matter.

## Why this release exists

The v0.4.x `runnerctl queue` feature protects a small self-hosted runner host by blocking a job in the GitHub runner's pre-job hook until a local slot is free. That protects CPU/RAM, but GitHub has already assigned the job at that point.

As a result, a job can look like this:

```text
GitHub UI: in progress
runnerctl: waiting for host slot
```

That distinction matters because the waiting period is inside the assigned job lifecycle and can consume part of a configured `timeout-minutes` budget.

v0.5.0 adds `runnerctl scheduler`, which moves admission **before GitHub assignment** by controlling a custom self-hosted-runner routing label. Excess jobs therefore remain in GitHub's normal `queued` state until host capacity is available.

## Before and after

### v0.4.x legacy admission gate

```text
queued
  -> GitHub assigns job
  -> in progress
  -> runnerctl pre-job hook waits for slot
  -> workflow steps run
```

### v0.5.0 scheduler

```text
queued
  -> no runner has runnerctl-scheduled label yet
  -> scheduler grants one routing label when capacity is free
  -> GitHub assigns job
  -> in progress
  -> workflow steps run
```

## Required workflow change

**The scheduler only controls jobs that request its routing label.**

Change jobs that should share the host capacity limit from:

```yaml
runs-on: [self-hosted, linux, x64]
```

to:

```yaml
runs-on: [self-hosted, linux, x64, runnerctl-scheduled]
```

Jobs that omit `runnerctl-scheduled` bypass the scheduler and may still execute concurrently.

## Migration from `runnerctl queue`

First upgrade runnerctl, then:

```bash
runnerctl queue status
runnerctl queue disable

runnerctl scheduler enable --max-concurrency 1
runnerctl scheduler status
```

For a low-memory host, start with `--max-concurrency 1`.

After adding `runnerctl-scheduled` to the workflow, trigger multiple jobs and verify that only admitted work is `in progress`; excess jobs should remain `queued` in GitHub Actions.

## New commands

```bash
runnerctl scheduler status [--json]
runnerctl scheduler enable [--max-concurrency N] [--interval SECONDS] [--label LABEL]
runnerctl scheduler disable
runnerctl scheduler tick [--json]
runnerctl scheduler run
runnerctl scheduler drain
runnerctl scheduler resume
```

`enable` performs an initial reconciliation before starting the controller. If GitHub state cannot be read safely, enable fails and the scheduler remains disabled.

`drain` stops granting new capacity. Busy runners are not interrupted. Idle scheduler labels are reclaimed.

`disable` stops the controller and removes scheduler routing labels; it does not unregister runners or kill an already-running job.

## Legacy `queue` is still available

`runnerctl queue` has **not** been removed. It is now explicitly documented as a **legacy host-side admission gate**.

Use it when you cannot change workflow labels and accept that waiting jobs may appear `in progress` and may spend job timeout budget while waiting.

The scheduler and the legacy queue cannot be enabled at the same time.

## How scheduling works

v0.5.0 supports runnerctl-managed **repository-level** self-hosted runners. The scheduler:

1. reads each managed runner's repository/account metadata;
2. polls recent queued/in-progress workflow runs and queued jobs;
3. counts only queued jobs that request the scheduler label;
4. reads GitHub runner online/busy/custom-label state;
5. grants the routing label to no more than `max-concurrency` eligible runners;
6. reclaims idle routing labels when capacity should be reassigned;
7. never intentionally revokes a busy runner merely for fairness.

Default routing label: `runnerctl-scheduled`.

## Polling, fairness, and API limits

v0.5.0 is a lightweight polling controller intended for small fleets.

- Default polling interval is 30 seconds.
- Scheduling is best-effort round-robin across managed repositories, **not strict global FIFO**.
- A just-finished runner can accept another job from the same repository before the next poll if it still holds the routing label.
- Concurrency remains bounded by routing labels granted, but perfect repository fairness is not guaranteed.
- Shorter polling intervals and more repositories increase GitHub API usage.

For larger fleets or lower-latency autoscaling, GitHub's `workflow_job` webhook and runner scale-set tooling are a better architecture than aggressive polling.

## Controller lifecycle

For convenience, `runnerctl scheduler enable` starts a local background controller.

That convenience controller is **not reboot-persistent in v0.5.0**. For a production host that must resume automatically after reboot, supervise:

```bash
runnerctl scheduler run
```

with systemd, launchd, Docker, or another process supervisor.

## GitHub permissions

The `gh` account associated with each managed repository must be able to:

- read Actions workflow run/job state;
- read repository self-hosted runner state;
- add/remove custom labels on repository self-hosted runners.

If runnerctl cannot obtain a complete state snapshot, reconciliation fails closed and does not grant additional capacity.

## Multi-account behavior

runnerctl continues to use the account stored in each managed runner's `.runnerctl-meta`. This allows one host to schedule runners belonging to different repositories/accounts, provided each saved account is still authenticated in `gh` and has the required repository permissions.

Organization-level and enterprise-level runner scheduling is not included in v0.5.0.

## Safety changes

- Manual `scheduler tick` is rejected while the background controller is running to prevent concurrent reconciliation.
- Scheduler control commands are serialized locally.
- Busy runners retain capacity during drain/rebalance.
- GitHub/API snapshot failure prevents new capacity grants.
- Scheduler and legacy queue modes are mutually exclusive.
- Existing custom/default runner labels are preserved; runnerctl only manages the configured scheduler label.

## Installation / verification

After upgrading:

```bash
runnerctl version
runnerctl scheduler --help
runnerctl scheduler status --json
runnerctl queue --help
```

Expected version:

```text
0.5.0
```

Before enabling the scheduler, update the relevant workflow `runs-on` labels and confirm the configured `gh` accounts have runner-label administration permission.

## Rollback

```bash
runnerctl scheduler disable
```

Then remove `runnerctl-scheduled` from workflow `runs-on` labels.

If you intentionally want the v0.4-style local gate again:

```bash
runnerctl queue enable --max-concurrency 1
```
