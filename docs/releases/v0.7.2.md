# runnerctl v0.7.2 — started-hook reliability and actionable notifications

v0.7.2 is a reliability hotfix for self-hosted runners that can appear stuck in GitHub Actions at **Set up runner** after a `job.started` notification has already been delivered.

## Why this release exists

GitHub executes `ACTIONS_RUNNER_HOOK_JOB_STARTED` synchronously after a job is assigned to a self-hosted runner but before workflow steps begin. GitHub does not provide a timeout for this hook.

runnerctl can compose multiple started handlers. A host that still has the deprecated v0.4 legacy admission gate enabled may therefore behave like this:

```text
GitHub assigns job
  -> runnerctl notify sends job.started
  -> legacy queue hook waits for a host slot
  -> GitHub UI remains in Set up runner / in progress
```

The old queue wait was effectively unbounded, and cancellation signals did not force the generated wait loop to terminate. This could make a cancelled Actions job appear stuck and leave confusing local wait state.

The notification was also misleading because `job.started` looked like workflow execution had begun even though it only meant the synchronous runner-start hook was executing.

## What changed

### Legacy queue waits are bounded

`runnerctl queue` remains a backwards-compatible legacy admission gate, but v0.7.2 adds a watchdog around its generated started hook.

Default maximum hidden wait:

```text
300 seconds
```

Override before enabling the legacy gate:

```bash
export RUNNERCTL_QUEUE_MAX_WAIT_SECONDS=120
runnerctl queue enable --max-concurrency 1
```

A wait that exceeds the configured limit exits with a clear error rather than remaining stuck forever.

### Cancellation now terminates the hidden wait

TERM, INT, and HUP terminate the watchdog, stop the legacy queue child process, and remove the runner's waiting/slot state.

Changing queue configuration still does **not** terminate a workflow job that has already acquired a slot and started running.

### `job.started` wording is now explicit

The event name remains `job.started` for compatibility, but human-readable notifications now say:

```text
[runnerctl] runner assigned / setup started
```

and include:

```text
note: workflow steps have not started yet; this is the synchronous runner setup hook.
```

This avoids claiming that build/test/deploy steps are already executing.

## Notification context is now actionable

Telegram and LINE messages now include the context needed to identify the exact run without opening multiple repositories manually:

```text
[runnerctl] runner assigned / setup started
event: job.started
runner: example-runner-01
repo: example-org/example-repo
branch: feature/example-change
workflow: CI
job: build_and_test
sha: 0123456789ab
run: 98765 (attempt 2)
url: https://github.com/example-org/example-repo/actions/runs/98765
note: workflow steps have not started yet; this is the synchronous runner setup hook.
```

The stable webhook/plugin JSON event also gains the same navigation metadata where available:

- `branch`
- `ref`
- `ref_type`
- short `sha`
- `run_attempt`
- `github_event`
- `actor`
- `server_url`
- `run_url`
- `phase`

For pull requests, runnerctl prefers `GITHUB_HEAD_REF` so the message shows the source branch instead of only the synthetic pull-request merge ref.

runnerctl deliberately does **not** perform an additional GitHub API request from the synchronous start hook merely to resolve a display job name. `GITHUB_JOB` plus the clickable run URL are used instead so the hook remains predictable and bounded.

## Custom notification plugins in runner hooks

Executable custom providers can still be used for manual `notify emit` / `notify test` operations.

However, custom executables are skipped by default when invoked from the synchronous GitHub runner hook. A plugin has no guaranteed network/runtime bound and could otherwise freeze `Set up runner` indefinitely.

An operator who has independently bounded and audited a plugin may explicitly opt in:

```bash
export RUNNERCTL_NOTIFY_ALLOW_CUSTOM_HOOK_PROVIDERS=1
```

Built-in Telegram, LINE, and webhook providers remain bounded by their short curl connect/total timeouts.

## New diagnostic command

Use:

```bash
runnerctl notify doctor RUNNER
```

or:

```bash
runnerctl notify doctor RUNNER --json
```

The command reports without exposing credentials:

- started/completed dispatcher paths;
- registered runnerctl started/completed handlers and their execution order;
- notification events enabled for the runner;
- legacy queue enabled/drained state;
- legacy queue max concurrency and max hidden wait;
- scheduler enabled state;
- notification failure log path;
- warnings for dangerous combinations.

Example warning:

```text
WARNING: legacy queue is enabled; GitHub Set up runner may wait up to 300s; prefer runnerctl scheduler
```

## Immediate recovery if a runner is stuck now

First inspect the runner:

```bash
runnerctl notify doctor YOUR_RUNNER
runnerctl queue status --json
runnerctl scheduler status --json
```

If the deprecated legacy queue is enabled and you intended to use the GitHub-native scheduler, disable the old gate:

```bash
runnerctl queue disable
```

Then make sure scheduled workflows use the scheduler routing label documented by `runnerctl scheduler --help`.

The important distinction is:

```text
runnerctl queue
  -> job already assigned by GitHub
  -> GitHub shows in progress / Set up runner
  -> local started hook waits

runnerctl scheduler
  -> runner routing capacity is controlled before assignment
  -> waiting jobs remain GitHub queued
  -> preferred production model
```

## Upgrade

Check first:

```bash
runnerctl upgrade --check --json
```

Then upgrade using the installation method already detected by runnerctl:

```bash
runnerctl upgrade
```

After upgrade:

```bash
runnerctl version
runnerctl notify doctor YOUR_RUNNER
```

Expected CLI version:

```text
0.7.2
```

If a runner's hook configuration was changed, restart that runner service so its `.env` hook configuration is reloaded.

## Compatibility

- Existing Telegram, LINE, webhook, Bot/API, scheduler, cleanup, and runner lifecycle commands remain supported.
- `job.started` remains the event identifier for backwards compatibility; only its rendered semantics are clarified.
- Existing custom plugins still work for manual delivery.
- The legacy queue remains available but is intentionally treated as compatibility mode.
- The GitHub-native scheduler remains the recommended queue mechanism.

## Rollback

If v0.7.2 must be rolled back, reinstall v0.7.1 using the same installation method. Be aware that rolling back also restores the old unbounded legacy-start wait behavior, so the safer rollback is to disable `runnerctl queue` and use the scheduler rather than relying on the old admission gate.
