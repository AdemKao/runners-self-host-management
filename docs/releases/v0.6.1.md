# runnerctl v0.6.1 — started-hook reliability and actionable job notifications

This patch release fixes a reliability problem where a GitHub Actions job could remain stuck in `Set up runner` after a `job.started` notification had already been sent.

## Root cause
GitHub executes `ACTIONS_RUNNER_HOOK_JOB_STARTED` synchronously and does not provide a built-in timeout. runnerctl composes notification and legacy admission-queue handlers in that hook. A legacy queue handler could therefore keep waiting for a host slot after the notification had already been delivered, making the message look as if the workflow had started even though workflow steps had not begun.

## Goals
- ensure cancellation terminates legacy queue waiting cleanly;
- add explicit diagnostics for started-hook composition and legacy queue state;
- make notification text include repository, branch/ref, workflow, job id, commit, event, and a clickable GitHub Actions run URL;
- clearly distinguish `job.assigned`/hook-start semantics from actual workflow-step execution;
- keep notification delivery bounded and fail-open;
- warn when the deprecated legacy admission gate is still enabled alongside notifications;
- provide migration guidance to the GitHub-native scheduler.

Implementation and final release notes will be completed by issue #26.
