# runnerctl v0.6.0 — notifications, monitoring, and integration providers

v0.6.0 adds an optional notification/integration layer for self-hosted runner operations.

The goal is to let an operator stop staring at the GitHub Actions UI while keeping runnerctl vendor-neutral: runnerctl emits a stable event, and Telegram, LINE, webhooks, or custom executable providers deliver it.

## What is new

### Notification CLI

```bash
runnerctl notify status [--json]
runnerctl notify providers [--json]
runnerctl notify test [--provider NAME|--all]
runnerctl notify emit EVENT [--message TEXT] [--runner NAME]
runnerctl notify enable RUNNER [--events LIST]
runnerctl notify disable RUNNER
```

### Built-in providers

- Telegram Bot API
- LINE Messaging API
- generic JSON webhook

### Provider plugins

Executable plugins can be placed under:

```text
$RUNNERCTL_HOME/plugins/notify/NAME
```

Each provider receives the same JSON event on stdin and the event/message in environment variables.

## Job notifications

Enable job lifecycle notifications for a managed runner:

```bash
runnerctl notify enable oracle-ci-01 \
  --events job.started,job.completed
```

runnerctl composes the notification handlers with the existing shared hook dispatcher. Cleanup and the legacy queue hook can continue to coexist with notifications.

Supported job events in v0.6.0:

- `job.started`
- `job.completed`

### `job.completed` does not claim success/failure

GitHub executes its completed runner hook before the job is fully finalized by GitHub. runnerctl therefore reports **completed**, not **succeeded** or **failed**.

This is intentional. v0.6.0 does not guess a job conclusion.

A future GitHub `workflow_job` webhook controller can provide authoritative success/failure events.

## Scheduler notifications

Successful scheduler control commands emit:

- `scheduler.enabled`
- `scheduler.disabled`
- `scheduler.drained`
- `scheduler.resumed`

A failing scheduler control command attempts to emit:

- `scheduler.error`

Notification delivery is best-effort and never changes the scheduler command's own exit status.

## Telegram configuration

```bash
export RUNNERCTL_TELEGRAM_BOT_TOKEN='...'
export RUNNERCTL_TELEGRAM_CHAT_ID='...'
runnerctl notify test --provider telegram
```

The bot token is treated as a secret. It is not returned by `notify status` or `notify providers`.

Telegram delivery uses Bot API `sendMessage`.

## LINE configuration

```bash
export RUNNERCTL_LINE_CHANNEL_ACCESS_TOKEN='...'
export RUNNERCTL_LINE_TO='U...'
runnerctl notify test --provider line
```

LINE delivery uses the Messaging API push-message endpoint. The target must satisfy LINE's push-message delivery conditions.

## Generic webhook

```bash
export RUNNERCTL_WEBHOOK_URL='https://example.com/hooks/runnerctl'
export RUNNERCTL_WEBHOOK_AUTH_HEADER='Authorization: Bearer ...' # optional
runnerctl notify test --provider webhook
```

The webhook receives a JSON document such as:

```json
{
  "schema_version": 1,
  "event": "job.completed",
  "timestamp": "2026-08-23T00:00:00Z",
  "host": "oracle-ci-01",
  "runner": "billing-runner-01",
  "repository": "example-org/example-repo",
  "run_id": "123456789",
  "run_attempt": "1",
  "job": "test",
  "workflow": "CI",
  "run_url": "https://github.com/example-org/example-repo/actions/runs/123456789",
  "message": "[runnerctl] job.completed ..."
}
```

Consumers should use `schema_version` and ignore unknown future fields.

## Selecting providers

When no explicit provider list is set, runnerctl selects fully configured built-in providers plus executable custom plugins.

Restrict providers with:

```bash
export RUNNERCTL_NOTIFY_PROVIDERS=telegram,webhook
```

## Failure behavior

GitHub runner hooks are synchronous and do not provide a separate hook timeout. Notification delivery therefore has deliberately conservative behavior:

- default connect timeout: 2 seconds;
- default total request timeout: 4 seconds;
- job-hook delivery: one attempt and fail-open;
- manual `notify test` / `notify emit`: one bounded retry and non-zero exit on final failure;
- provider failures are logged without intentional credential values.

A notification provider outage should not turn a successful CI workload into a failed workload.

## Security model

Provider credentials are read from environment variables rather than positional CLI arguments or normal runnerctl configuration files.

Sensitive values include:

- `RUNNERCTL_TELEGRAM_BOT_TOKEN`
- `RUNNERCTL_LINE_CHANNEL_ACCESS_TOKEN`
- `RUNNERCTL_WEBHOOK_AUTH_HEADER`

Recommended deployment:

- inject secrets through a secret manager or protected service-manager environment file;
- restrict secret files to the runner service account;
- do not commit provider secrets to workflow YAML or the repository;
- do not dump runner service environments into CI logs.

`notify status --json` exposes configuration booleans, not credential values.

## Custom provider contract

A custom executable provider receives:

- event JSON on stdin;
- `RUNNERCTL_NOTIFY_EVENT`;
- `RUNNERCTL_NOTIFY_MESSAGE`;
- `RUNNERCTL_NOTIFY_HOOK=1` for runner-hook delivery.

Exit code `0` means successful delivery. Non-zero means delivery failure.

Plugins should implement short network timeouts, especially when `RUNNERCTL_NOTIFY_HOOK=1`.

## Monitoring/query scope

v0.6.0 adds local inspection:

```bash
runnerctl notify status
runnerctl notify status --json
runnerctl notify providers
```

This is operational state/configuration inspection, not a historical metrics database.

Notification delivery failures are recorded in:

```text
$RUNNERCTL_HOME/notify/notify.log
```

## Why Telegram/LINE `/status` bot commands are not included yet

Inbound bot commands require a different architecture from outbound notifications.

Telegram inbound commands require long polling or a webhook. LINE inbound commands require a Messaging API webhook. A production implementation also needs:

- request/signature validation;
- authorized user/chat allowlists;
- replay and rate-limit protection;
- a persistent controller process;
- potentially a public HTTPS endpoint;
- explicit rules for read-only versus mutating commands.

v0.6.0 deliberately ships the outbound event/provider foundation first. A later bot/API controller can safely call existing runnerctl JSON commands such as scheduler/notification status without redesigning providers.

## Installation verification

After upgrading:

```bash
runnerctl version
runnerctl notify --help
runnerctl notify providers
runnerctl notify status --json
```

Expected version:

```text
0.6.0
```

Then configure **one provider at a time** and run its test command before enabling runner hooks.

## Suggested rollout

1. Upgrade runnerctl.
2. Configure one provider secret/destination.
3. Run `runnerctl notify test --provider ...`.
4. Check `runnerctl notify status`.
5. Enable notifications on one non-critical runner.
6. Trigger one job and verify `job.started` / `job.completed` delivery.
7. Expand to other runners.

## Rollback

Disable notifications per runner:

```bash
runnerctl notify disable RUNNER
```

Then remove provider environment variables and restart the runner service if necessary.

Notifications do not require workflow YAML changes, so rollback does not require repository workflow edits.
