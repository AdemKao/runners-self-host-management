# runnerctl v0.7.0 — read-only Telegram, LINE, and HTTP API controller

v0.7.0 adds the inbound/query side of runnerctl integrations.

v0.6.0 introduced outbound notifications:

```text
runnerctl -> Telegram / LINE / webhook
```

v0.7.0 adds a deliberately read-only controller:

```text
Telegram / LINE / authenticated HTTP client
  -> fixed read-only command router
  -> runnerctl JSON queries
  -> response
```

The most important design decision in this release is that **remote mutation is not available**. The controller is an observability interface, not a remote administration shell.

## New commands

```bash
runnerctl bot status [--json]
runnerctl bot doctor [--json]
runnerctl bot query status|runners|queue|scheduler|health [--json]
runnerctl bot telegram run [--once]
runnerctl bot serve [--bind HOST] [--port PORT] [--allow-remote]
```

Bot/API functionality requires **Python 3.8 or newer** and only uses the Python standard library. Python is optional for runnerctl as a whole: runner registration, scheduler, queue, cleanup, notifications, and other existing features continue to work without it.

## Read-only command contract

Remote input is mapped only to this fixed list:

```text
/status
/runners
/queue
/scheduler
/health
/help
```

The controller does not pass arbitrary text to a shell and does not construct arbitrary runnerctl argument lists from chat messages.

Examples intentionally rejected as unsupported include:

```text
/drain
/resume
/stop
/remove
/status; command
$(command)
```

v0.7.0 does **not** expose scheduler drain/resume, runner start/stop/remove, authentication changes, upgrades, or any other mutating command through Telegram, LINE, or the HTTP API.

## Query sources

| Remote command | Read-only source |
| --- | --- |
| `status` | aggregate runner/queue/scheduler/notification snapshots |
| `runners` | `runnerctl list --json` |
| `queue` | `runnerctl queue status --json` |
| `scheduler` | `runnerctl scheduler status --json` |
| `health` | `runnerctl doctor --json` |
| `help` | controller command list |

## Telegram long polling

Telegram uses the Bot API `getUpdates` long-polling mechanism. A Telegram deployment therefore does **not** require a public inbound port.

Configure:

```bash
export RUNNERCTL_TELEGRAM_BOT_TOKEN='...'
export RUNNERCTL_TELEGRAM_ALLOWED_CHAT_IDS='123456789'
```

Multiple allowed chat IDs can be comma-separated.

For compatibility with the v0.6 notification provider, if `RUNNERCTL_TELEGRAM_ALLOWED_CHAT_IDS` is absent, `RUNNERCTL_TELEGRAM_CHAT_ID` is used as the single allowed chat when configured.

Run one cycle for diagnostics:

```bash
runnerctl bot telegram run --once
```

Run continuously:

```bash
runnerctl bot telegram run
```

Telegram update replay is limited using a persisted offset at:

```text
$RUNNERCTL_HOME/bot/telegram.offset
```

The offset is advanced for received updates even when a message comes from a chat that is not authorized, so rejected updates do not remain stuck and replay forever.

## HTTP JSON API

Start the controller locally:

```bash
export RUNNERCTL_BOT_API_TOKEN='use-a-long-random-value'
runnerctl bot serve
```

Default bind:

```text
127.0.0.1:8765
```

Endpoints:

```text
GET /v1/status
GET /v1/runners
GET /v1/queue
GET /v1/scheduler
GET /v1/health
GET /healthz
POST /v1/line/webhook
```

The `/v1/*` query endpoints require:

```text
Authorization: Bearer <RUNNERCTL_BOT_API_TOKEN>
```

Bearer comparisons use a constant-time comparison routine.

`/healthz` returns only minimal health information. It may be unauthenticated on a loopback bind; when the controller is bound outside loopback it also requires the bearer token.

## Remote bind protection

runnerctl refuses this by default:

```bash
runnerctl bot serve --bind 0.0.0.0
```

Non-loopback binding requires **both**:

1. `--allow-remote`
2. `RUNNERCTL_BOT_API_TOKEN`

Example:

```bash
export RUNNERCTL_BOT_API_TOKEN='use-a-long-random-value'
runnerctl bot serve --bind 0.0.0.0 --port 8765 --allow-remote
```

runnerctl does not terminate TLS. If remote access is required, put the controller behind a trusted HTTPS reverse proxy, VPN, or tunnel. Do not expose an unauthenticated raw controller listener to the public Internet.

## LINE inbound commands

LINE uses an inbound webhook at:

```text
POST /v1/line/webhook
```

Configure:

```bash
export RUNNERCTL_LINE_CHANNEL_SECRET='...'
export RUNNERCTL_LINE_CHANNEL_ACCESS_TOKEN='...'
export RUNNERCTL_LINE_ALLOWED_USER_IDS='U0123456789abcdef0123456789abcdef'
```

The webhook validates `x-line-signature` with HMAC-SHA256 against the exact raw HTTP request body **before parsing the JSON**.

Invalid or missing signatures return HTTP 401 and are never processed as commands.

The sender must also appear in `RUNNERCTL_LINE_ALLOWED_USER_IDS`. A correctly signed webhook from an unapproved user is acknowledged but ignored.

A correctly signed webhook with an empty `events` array returns HTTP 200 so LINE webhook connectivity verification is supported.

LINE requires a publicly reachable HTTPS webhook URL. A recommended deployment shape is:

```text
LINE Platform
  -> https://runner.example.com/v1/line/webhook
  -> trusted TLS reverse proxy/tunnel
  -> http://127.0.0.1:8765/v1/line/webhook
```

Source IP is not used as the trust mechanism; signature verification and the user allowlist are the authentication boundaries.

## Security summary

v0.7.0 includes these safeguards:

- read-only remote command set;
- fixed command-to-runnerctl mapping;
- no shell interpolation of chat text;
- Telegram chat-ID allowlist;
- persistent Telegram update offset;
- mandatory LINE HMAC signature verification;
- LINE user-ID allowlist;
- HTTP bearer authentication;
- constant-time token/signature comparisons;
- 64 KiB inbound request size limit;
- loopback HTTP bind by default;
- explicit opt-in for remote bind;
- no credential values in `bot status` / `bot doctor`;
- no TLS claims: external HTTPS termination is required when public exposure is needed.

## Credentials

The controller reuses existing v0.6 outbound credentials where appropriate:

```text
RUNNERCTL_TELEGRAM_BOT_TOKEN
RUNNERCTL_LINE_CHANNEL_ACCESS_TOKEN
```

New inbound/security configuration:

```text
RUNNERCTL_TELEGRAM_ALLOWED_CHAT_IDS
RUNNERCTL_LINE_CHANNEL_SECRET
RUNNERCTL_LINE_ALLOWED_USER_IDS
RUNNERCTL_BOT_API_TOKEN
```

Do not put these values in issue comments, workflow logs, command history, or world-readable configuration files.

## Controller supervision

Telegram long polling and the HTTP/LINE controller are long-running processes. Production installations should supervise them with systemd, launchd, or an equivalent process supervisor.

Example systemd command for Telegram:

```text
ExecStart=/usr/local/bin/runnerctl bot telegram run
```

Example API/LINE command:

```text
ExecStart=/usr/local/bin/runnerctl bot serve --bind 127.0.0.1 --port 8765
```

Store environment secrets in a protected environment file, normally mode `0600`, according to the host's normal service-management policy.

## Relationship to the scheduler and notifications

No existing mode is replaced:

```text
runnerctl scheduler
  GitHub-native queued-job admission

runnerctl notify
  outbound events and alerts

runnerctl bot
  inbound read-only queries and replies
```

The bot controller calls the existing structured read-only commands. It does not create another runner scheduler or queue implementation.

## Failure behavior

- Telegram polling/network failures do not affect GitHub Actions jobs.
- Bot/API availability is independent of runner execution.
- A failed runnerctl read-only query returns an error rather than falling back to an unsafe command.
- A LINE reply-delivery failure is logged without exposing credentials; the signed webhook request can still be acknowledged.
- Unauthorized Telegram chats and LINE users cannot execute even read-only queries.

## Migration from v0.6.0

No migration is required for existing notification users.

After upgrading:

```bash
runnerctl version
runnerctl bot doctor --json
runnerctl bot query status --json
```

Expected version:

```text
0.7.0
```

Then enable only the integration you need.

Telegram users can start long polling without modifying firewall or reverse-proxy configuration.

LINE users must configure a signed HTTPS webhook route before starting inbound queries.

## Rollback / disable

The controller does not alter runner registration, queue slots, scheduler configuration, or runner hooks.

To disable Telegram inbound queries, stop the supervised `runnerctl bot telegram run` process.

To disable the HTTP API/LINE webhook, stop `runnerctl bot serve` and remove the external reverse-proxy/tunnel route. For LINE, also disable or remove the webhook URL in the LINE Developers Console if appropriate.

The existing `runnerctl notify` outbound notification feature continues independently.

## Not included in v0.7.0

Remote mutation is intentionally out of scope, including:

```text
/drain
/resume
/start
/stop
/restart
/remove
/upgrade
```

If these are added in a future release, they require a separate permission model, explicit authorization, audit logging, replay protection, and stronger confirmation semantics. The v0.7 bearer token/chat allowlists alone are not treated as sufficient authorization for destructive remote operations.
